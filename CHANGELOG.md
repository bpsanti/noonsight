# Changelog

## Unreleased

- The rule effect experiment (`experiments/rules`) can run an arm that delivers one preset rule alone: an arm with `only` in `plan.json` is the preset with every other rule that ships on for the model in `disable`, and the runner refuses a model whose preset lacks that rule before anything is spent.
  The design `single-rule` (`--design single-rule`) runs Sonnet 5.5 and Haiku 5.5 on `fix` and `bug` with `verify-changes` alone, `carry-through` alone, both and neither, 30 runs per arm, so the tests and the cost the `rules` arm added on 2026-11-19 can be credited to each rule; its fourteen comparisons are fixed before it runs, and `npm run experiment -- estimate --design single-rule` projects $11.64 against a $20 cap.
  A comparison of a design can now name its two arms, compare the cost per run, and leave the direction open where the rule's source claims none, in which case it is read as the direction found.
  The summary shows every arm that delivered a rule against `none`, and for a design with more than two arms a table of each arm's tests and cost against `none`, as a part of the `rules` arm's difference.
  The stub now runs the tests only when the session received a `verify-changes` rule, which it reads from noonsight's envelope, so it plays an arm of one rule as that rule alone.

- `noonsight report` now reads the configuration with the project of the directory it runs for laid over it, as `noonsight check` and `noonsight models` do.
  It read the machine's configuration alone, so a trusted project's rules were counted from the decision log but had no `text` length, and a project rule on for a model that never received it was left out of the rules never delivered, so a project rule that stopped reaching a model went unnoticed.
  The report's second line names the project and what became of it (`project` in `--json`), and the heading of the rules never delivered names the project file when it applied, since the log holds the sessions of every project.
  The rules `noonsight trust`, `check` and `models` list for an applied project are now those the merged configuration gives a model, not every rule the project file writes: a rule for a model the machine leaves out is only noted.
  See `docs/hooks.md` ("The decision log").

- The rule effect experiment (`experiments/rules`) has three fixtures and four tasks of different shapes: the read-only question and the one-file fix, a bug known only by its symptom whose cause is in another module, and a feature across several files, each with a hidden check and a reference solution that `npm test` checks against it.
  The design `expanded` (`--design expanded`) runs the three rules whose effect showed on 2026-11-16 on three tasks each, 30 runs per arm, with twelve comparisons fixed before it runs and read with Fisher's exact test or the Mann-Whitney U test and Holm's adjustment; `npm run experiment -- estimate` prints its cost projection, $78 expected against a $120 cap.
  `run --stub` runs every session against a scripted local stand-in for the API, with no login and no tokens, so the harness is checked end to end for free.
  A run cut short by the cap now stops at the first run that does not fit, so every cell keeps the same number of repetitions, instead of going on with cheaper models.
  `experiments/rules/results/2026-11-19/README.md` records its first run: 540 runs for $73.82, nine of the twelve comparisons supporting the rule's source and none against it; the verify rules changed behavior only where the models skipped the tests without them, and the preset is unchanged.

- A `/model` switch's delivery is no longer taken as received.
  Claude Code adds what the `PostModelSwitch` hook returns to the next request only, and drops it when another `/model` or the end of the session comes first; the hook recorded it as delivered all the same.
  So in a session started on Haiku, after `/model sonnet` and `/model fable` with no request between them, Fable read Haiku's rules from the session's start with no note saying they no longer applied, and a conversation resumed on the model a lost switch chose logged `already-delivered` and never got its rules.
  The session's record now keeps every model whose rules the conversation may hold without a note after them: each later note names all of them (`from` lists them, or reads `*` when their names do not fit), and a resume after a switch delivers the rules again.
  `noonsight report` no longer counts as delivered a switch whose session's next line is another switch, and lists it as `switched-again`.
  See `docs/hooks.md` ("PostModelSwitch").

- A conversation resumed with `claude --continue` or `claude --resume` without `--model` or `ANTHROPIC_MODEL` now gets the rules of the model it runs on when the `model` setting names another.
  Claude Code resumes such a conversation on the model of its last response since its last compaction, and only without one on the `model` setting, which `/model` in any session changes; the hook took the setting first, so a conversation that last answered on Opus, resumed after the setting became Haiku, got Haiku's rules and a note that Opus's no longer applied.
  At `resume` and `fork` the order is now `--model`, `ANTHROPIC_MODEL`, the conversation's last response read from the transcript (`model_source: "session-transcript"`), the `model` setting, then the session's record; an explicit `--model` keeps outranking the conversation.
  See `docs/hooks.md` ("SessionStart").

- The `claude` preset, version 1.3.1: `haiku-5-5/carry-through` and `sonnet-5-5/stay-in-scope` end with a sentence that makes what the project's own instructions explicitly require, in its instruction files or in the documents they point to, part of the request, and says a convention they only describe is not a requirement.
  Both rules tell the model to leave out what nobody requested, and a requirement that sat in a document the project's CLAUDE.md points to was often skipped as unrequested.
  In 610 runs of `experiments/rules`, Haiku with the previous wording met such a requirement in 44 of 60 runs and with this one in 59 of 60, and added nothing unrequested in 60 of 60 runs of a task where the project only describes a convention; a shorter wording reached 30 of 30 but added unrequested changes in 12 of 30.
  Sonnet showed no measurable change; the sentence is there for consistency.
  `experiments/rules/results/2026-11-18/README.md` records the run.
  `presets/claude/SOURCES.md` records the deviation from the guides' text; `noonsight check` reports the change to a configuration last checked against 1.3.0.

- A conversation resumed with `claude --continue` or `claude --resume` and an explicit `--model` now gets the rules of the model it runs on.
  Claude Code reports no model when it resumes a conversation, and runs it on the model its `--model`, `ANTHROPIC_MODEL` or `model` setting names, falling back to the conversation's own model only when none names one; the hook took the model from the session's record first, so a conversation that last ran on Haiku and was resumed with `--model sonnet` kept Haiku's rules and logged `already-delivered`, without a warning.
  At `resume` and `fork` the launch now comes before the record, and when the record is for another model, the new model's rules come with a note that the earlier ones no longer apply, as after `/model`; the log line names the record's model in `from_model`.
  See `docs/hooks.md` ("SessionStart").

- A user rule can replace a preset rule: `replaces`, on a rule in `models.<id>.add` of a model declared with `"use": "preset"`, names the preset rule, which is then off, and the user rule is delivered in its place, with its scopes, places and triggers unless it gives its own.
  Until now that took `disable` plus `add`, which did not say that one replaces the other.
  `noonsight models` lists the pair, the preset rule `replaced by` the user rule that follows it (`replaced_by` and `replaces` in `--json`).
  A `replaces` that names no preset rule of the model refuses the configuration, so `noonsight check` reports it; a preset rule is replaced once at most, and a replaced rule is neither enabled nor disabled.
  On a preset update, `replaces` follows a renamed rule as `enable` and `disable` do, and the change warning names the id to write; a change to the scopes, places or triggers of a replaced rule that the user rule takes is reported, and under `warn`, a `replaces` for a rule the update removed is reported, not refused.
  See `docs/configuration.md` ("Replacing a preset rule").

- Project configuration: a repository can commit `.noonsight/noonsight.json`, with its rule files, so that every contributor's sessions receive its rules.
  The file takes the keys of the machine's configuration except the preset keys and `projects`, and it is laid over the machine's configuration for the sessions that run in the project: the nearest file from `CLAUDE_PROJECT_DIR` (else the hook input's `cwd`, or the directory a command runs in) up to the repository root.
  A cloned repository applies only once the account trusts it: `noonsight trust` records the project directory, and later changes to its files apply without asking again, like Claude Code's folder trust; until then each new session in it starts with a warning, and `noonsight untrust` declines it quietly.
  The machine's configuration decides how far a project may go with `projects.allow`: `none` ignores project files, `add` (the default) lets a project only add rules for the models the machine declares, `rules` also lets it change which rules a model receives and declare scopes, and `all` also lets it set routing, the classifier and the subagent settings.
  Rule lists add up, the machine's rules first; a model entry with the machine's `use` merges into it, and one with another `use` replaces it; every other value the project writes replaces the machine's, key by key.
  A project rule's `replaces` needs `rules`; a project rule that takes the place of a machine rule keeps the preset rule that rule replaced off, and one that replaces the same preset rule as a machine rule wins.
  A project with any problem, alone or merged, is refused alone, and sessions receive the machine's configuration with a warning.
  `noonsight check`, `models`, `resolve` and `run` read the project of the directory they run for, and the decision log records `project` and `project_status`.
  See `docs/configuration.md` ("Project configuration").

- Preset updates no longer change the rules sessions receive without notice.
  The configuration records the preset version it was last checked against, `preset_version`, which `noonsight init` (and so `noonsight install`) writes.
  When the installed preset is another version, `noonsight check` lists, for each model declared with `"use": "preset"`, the rules now on (new, or shipping on now), the rules now off (removed, or shipping off now), renamed and changed rules, new rules that ship off, and the `enable` and `disable` entries that no longer name a rule; a new session whose model's rules changed starts with a warning that names them, and its decision log line records `preset_update`.
  `on_preset_change` chooses what an update does: `warn` (the default) delivers the installed version's rules, and `hold` keeps delivering the rules, scopes and routing table of `preset_version` until the user accepts the update.
  `noonsight accept` lists what the installed version changes and writes it to `preset_version`, changing only that value of the file; it writes nothing while the configuration would be refused with the installed version.
  The package keeps a copy of every earlier released version of its preset, from 1.3.0 on, in `presets/<preset>/versions/`, and a preset rule lists the ids it had before in `renamed_from`, so an `enable` or `disable` entry with an old id still applies and a rename is reported as one.
  Under `warn`, an `enable` or `disable` entry that names a rule the update removed is left out and reported instead of refusing the whole configuration.
  A configuration without `preset_version` works as before, and `noonsight check` warns until `noonsight accept` records one.
  See `docs/configuration.md` ("Preset updates").

- Rules for every model in one block: `all_models.add` takes the same rules as `models.<id>.add` (`id`, `file`, `scopes`, `where`, `triggers`) and delivers them to every model declared with `"use": "preset"` or `"use": "custom"`, after the preset's rules and before the model's own `add`, so team conventions no longer have to be repeated under each model.
  A model declared `"use": "none"`, by an exact key or a wildcard, receives none of them, and the block declares no model.
  A rule id must be new for each model that receives it, across the preset's rules, the block and the model's own `add`; the delivery limit of 9,500 characters is checked for each model with the block's rules among its rules, and the problem names the model it overflows.
  `noonsight models` lists the block and marks its rules under each model (`all_models` in `--json`, `from` on a rule), and `noonsight check` reports the models that receive it.
  See `docs/configuration.md` ("Rules for every model").
- Triggers: a rule can list `triggers`, actions that also deliver it to a session whose scope is not one of the rule's scopes, once the session does one; a plain interactive session has no scope, so every rule written for a list of scopes used to stay dormant in it.
  The one trigger is `code-edit`: the session edits, with Edit or Write, a file with a code extension that the git repository of its project, or of one of its worktrees, already tracks, so reports, notes, `.md` and `.html` files, new files, ignored files and files outside the project never count.
  A sixth hook entry, `PostToolUse` on `Edit|Write`, delivers the rules the trigger adds with the first such edit, as `additionalContext`, which Claude Code adds right after the edit's result; it runs `git ls-files` and `git rev-parse` until the session reveals the trigger, and nothing after.
  A session's triggers only grow: they hold after compaction, a resume and a `/model` switch, and only the rules a trigger adds are delivered, once.
  A rule that lists a trigger must not be for every scope, and must be for the place `session` or `unattended`.
  Run `noonsight install` again: `noonsight check` reports an install without the `Edit|Write` entry.
  See `docs/configuration.md` ("Triggers") and `docs/hooks.md` ("PostToolUse on Edit and Write").
- The `claude` preset, version 1.3.0: `sonnet-5-5/verify-changes` and `haiku-5-5/verify-changes` list `code-edit`, so a Sonnet or Haiku session receives them with its first edit of a tracked code file, whatever its scope. Only rules that are cheap when the edit was not what their scopes mean list a trigger; `presets/claude/SOURCES.md` ("Rules delivered on an action") gives the reasoning, a judgment, rule by rule.
- The decision log records `file-edit` lines (`trigger`, `file`), `triggers` on session lines of a session that revealed one, and `triggered_rules`, the rules a trigger brought; `noonsight report` shows, for each rule, what brought its deliveries, and the triggers sessions revealed with the tools, extensions and files of the edits; `noonsight models` lists each rule's triggers, and `noonsight check` the rules each trigger delivers.

- `noonsight install` is now the one command that sets noonsight up: when there is no configuration file it writes one as `noonsight init` does, never replacing an existing file, then installs the hooks as before, runs `noonsight check`, lists the rules each declared model receives, and says what it changed or that nothing changed.
  Running it again changes nothing.
  It exits 2 when the configuration is refused and 1 when it cannot write the configuration file, where it used to exit 0 once the hooks were in; a problem the check reports elsewhere on the machine is printed and leaves the status at 0.
  `--managed` still installs only the hooks, and so does the watcher for each new login.
  The step-by-step commands (`init`, `models`, `install`, `check`) all still work.

- The benchmark pilot in `experiments/benchmark/` (`npm run benchmark`): SWE-bench Verified tasks with a native arm64 image, Terminal-Bench 2.1, ReviewBench, SWE Atlas and issue digests, run through Harbor with an agent that installs noonsight in each task's container, on Fable 5.2, Opus 5.5, Sonnet 5.5 and Haiku 5.5 under `off` and `on`. Tasks are chosen with a fixed seed, and a free gold check runs each reference solution here first and replaces the tasks that fail. The runner works one night at a time, in a fixed priority order, within a per-run budget, a per-night budget, a total cap and a floor on the account's weekly quota, and resumes after an interruption without losing or repeating a run. Open tasks are graded by a Claude Opus 5.5 judge, calibrated against the author's blind grades. The plan is pre-registered in `experiments/benchmark/preregistration.md`.
- The benchmark pilot compares noonsight with the usual alternative: `claudemd` puts every model's rules in one user `CLAUDE.md` with noonsight off, and `scattered` puts them in a file that `CLAUDE.md` only points to; they replace the pre-registered placebo, which had not run. `NOONSIGHT_LIVE_DELIVERY=1 npm run test:live` runs the delivery probe: interactive sessions against a local stand-in for the API that records every request, which shows where each condition's rules reach the model (session start, three kinds of subagent, `/model`, `/compact`, `/clear`) without sending anything to Anthropic.
- The benchmark pilot's results, `experiments/benchmark/results/2026-11-19/`: 588 runs on 21 tasks under `off`, `on`, `claudemd` and `scattered`, read for delivery first. noonsight put each model's own rules in every path the delivery probe checks, and other models' rules in none except after a model switch, where the earlier model's rules stay in the history alongside noonsight's note; one `CLAUDE.md` with every model's rules missed the Explore and Plan subagents and carried the other models' rules wherever it reached, so only 18 to 29 percent of the rule text a model received was written for it; a pointer to a rules file delivered nothing unless the agent opened the file. In the paid runs every condition delivered what it is meant to. A run cost 7, 19 and 25 percent more under `on`, `claudemd` and `scattered` than under `off`; the verifier saw no measurable difference between the conditions on this task set, and the judge's scores of the open answers are not calibrated yet. `npm run benchmark -- summarize --results <dir>` prints the tables of a results folder, including the pre-registered share of the delivered rule text written for the receiving model, per run and per probe path.
- The delivery benchmark in `experiments/delivery/` (`npm run delivery`): real interactive Claude Code sessions against a local stand-in for the API, with no login and no tokens, checked request by request against an invariant (each model's right rules are in every request it receives, its own rules are not retired by a later note, and another model's rules are there only with a note that retires them) and measured for coverage, precision, cost in text and hook time, and robustness.
  It runs at three levels: a corpus of short sequences with the outcome each must have (`NOONSIGHT_LIVE_DELIVERY=1 npm run test:live`), a fuzz level of random lifecycle sequences from a seed (`/model`, `/compact`, `/clear`, resumes, parallel subagents, file edits) under noonsight and under a `CLAUDE.md`, `.claude/rules` and a skill per model, and a self-check where failures planted in a copy of the hook must be caught and shrunk.
  Results are kept per Claude Code version; the first, for 2.1.328, is in `experiments/delivery/results/claude-code-2.1.328/`.
  The corpus keeps the shortest reproductions of the two failures the fuzzer found, a `/model` delivery lost before any request and a resume given the `model` setting's rules, which pass since the fixes of `/model` deliveries and resumed conversations in this release, and one documented limit, a compacted conversation resumed on Claude Code's default model.
- A subagent's rules now reach it through a fifth hook, `SubagentStart`, as `additionalContext`, instead of being added to the end of its task text: the agent call hook no longer changes a call it only gives rules to.
  In auto mode, a call a hook changed left the other calls of the same response without the classifier's verdict, so a Bash call or another subagent made next to it was refused until Claude made it again; those calls now run.
  A call routing changes is still returned changed, with `subagents.permission`, so with routing on in auto mode a routed call still has that effect (see `docs/hooks.md`, "Routing").
  `SubagentStart` does not name the call that started the subagent, so the hook takes the one open call of the subagent's type in the session, or the call whose result already named the subagent; when several calls of the type are open and no result names it within two seconds, the subagent gets only the rules all of them would give, never another call's, since the subagents of one response start in no fixed order.
  A call whose subagent never starts, because something denied it after the hook ran, stays open for 2 minutes, or until a call of its type comes more than 5 seconds after it.
  When the call's record cannot be written, a call routing changed is still returned changed, and its subagent gets no rules (`error` on the `agent-call` line, with a warning).
  Run `noonsight install` again: `noonsight check` reports an install without the `SubagentStart` entry, whose subagents get no rules.

- The project is renamed from sextant to noonsight: the package `sextant-ai` is now `noonsight`, the command `sextant` is now `noonsight`, and the repository is `github.com/bpsanti/noonsight`.
  Every `SEXTANT_*` environment variable is now `NOONSIGHT_*`; the configuration is `~/.config/noonsight/noonsight.json`, the state and the decision log are in `~/.local/state/noonsight/`, the hook pointer is `noonsight-hook` (in `~/.local/share/noonsight/`, or the system directory of a machine-wide install), the machine-wide drop-in is `managed-settings.d/noonsight.json`, the watcher's service is `io.github.bpsanti.noonsight.watch` (`noonsight-watch.service` on Linux), the configuration schema is `schema/noonsight.schema.json`, and the rules arrive in `<noonsight-rules>` tags.

- The classifier, off by default: `classifier.mode` (`off`, `fallback`, `always`), `classifier.model` (`haiku`), `classifier.effort` (`low`) and `classifier.timeout_ms` (8000, at most 8000 so the agent call hook still answers within Claude Code's 10-second limit). An `--append-system-prompt` someone else passes is kept, and an `--append-system-prompt-file` is merged into the launcher's file, since Claude Code keeps only the last one. Each launch logs an `event: "launch"` line. See `docs/launcher.md`.
- `SessionStart` recognizes the rules `noonsight run` put in the system prompt: at `startup`, `clear` and `compact`, when the Claude Code process was started with the launcher's file and the file holds the rules the hook decided on, it delivers nothing and logs `delivered: "launcher"`. When the launcher's rules are for another model, it delivers the session's model's rules with a note that the others do not apply.
- Live tests for the launcher (`NOONSIGHT_LIVE_LOGIN=1 npm run test:live`): an explicit model with the hooks, `claude -p` without them, and another `--append-system-prompt` or `--append-system-prompt-file` on the same command line.
- The `claude` preset, version 1.0.0: 16 rules for `claude-fable-5-2`, `claude-opus-5-5`, `claude-sonnet-5-5` and `claude-haiku-5-5`, each adapted from Anthropic's prompting guide for that exact model, and five scopes, `investigate`, `build`, `review`, `routine` and `digest`, with descriptions and no matchers. Eight rules ship on and eight off. No rule is delivered in a place where Claude Code 2.1.325 already sends the same advice: `fable-5-2/finish-work` reaches subagents only, because Fable 5.2 sessions already get it. `presets/claude/SOURCES.md` gives the source, effect and cost of every rule.
- Preset format: every rule must state `effect` and `cost` besides its `source`, every preset scope a `description` and a `source`, and a preset can record under `claude_code` the Claude Code version its rules were compared with. A preset rule must fit the delivery limit on its own, and a model's preset rules together with every rule on, so turning on a rule never makes a configuration too long.
- `noonsight init` writes the configuration file from the preset, declaring each of its models with `"use": "preset"`; it never replaces an existing file.
- `noonsight models` lists each declared model with every rule it can receive, on or off, with source, effect and cost; the preset's models that are not declared; and the models the decision log has seen that are not declared. `--json` prints the same as JSON.
- Live tests for the preset (`NOONSIGHT_LIVE_LOGIN=1 npm run test:live`): `system-prompt` reads the system prompt Claude Code sends each of the four models, in a session and in a subagent, and fails when a preset rule is delivered where Claude Code already gives its advice, or when what Claude Code sends changes; `preset-hash` checks that the real preset reaches a session and a subagent and that the decision log records the hash `noonsight resolve` gives.
- The installed preset's scopes are now declared for every configuration, since the package ships one.
- Task scopes: a scope can declare `match`, regular expressions run case-insensitively over a subagent's description and task text; the preset's scopes can declare them too, and a user scope of the same name replaces only the keys it gives. A session takes its scope from `NOONSIGHT_SCOPE`; a subagent from the scope whose matcher matches earliest in its task, and never from the session. An undeclared scope only means the rules for every scope. See `docs/configuration.md`.
- Place: `session.unattended_when_env` lists environment variables that put a session in the place `unattended`, so it receives the rules declared for sessions nobody is watching.
- The decision log records `scope`, `place`, `scope_source`, and when they apply `unknown_scope`, `scope_matcher`, `unattended_env` and `task_text_cut`.
- `noonsight check` reports two scopes whose matchers match the same example text, and says which scope and place sessions started from its environment get. A matcher that is not a valid regular expression, that matches every plain task text, or that has a shape known to backtrack catastrophically (a leading `.*` with no `^`, nested unbounded quantifiers such as `(a+)+`, or overlapping unbounded quantifiers in a row such as `\w+\w+`) refuses the configuration, naming the scope and the pattern.
- Live tests for scopes (`NOONSIGHT_LIVE_LOGIN=1 npm run test:live`): two sessions and two subagents on the same model, in two scopes, return different verification words.
- `noonsight watch enable` and `noonsight watch disable`: an optional watcher, off by default, that installs the hooks into each new Claude Code configuration directory made in the home directory, as `noonsight install --account <dir>` does. It runs as a launchd agent on macOS and a systemd user service on Linux, and watches only the entries directly in the home directory. `noonsight check` says whether it is on and runs. The first session of a brand-new login can still start without the rules; see `docs/install.md`.
- Subagent hooks: `PreToolUse` on the agent tool (matcher `Agent|Task`) predicts the model each subagent will run on, in Claude Code's order (fork, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, the call's `model`, the subagent's definition, the built-in subagents' own models, `CLAUDE_CODE_SUBAGENT_MODEL`, the parent's model), and adds that model's rules for the place `subagent` to the end of the subagent's task text. It never changes the model or the effort. `PostToolUse` compares the prediction with the model the subagent started on (`resolvedModel`), logs `match` or `MISMATCH`, and warns on a mismatch. An undeclared or unknown model only warns. See `docs/hooks.md`.
- Configuration: `subagents.delivery` (`prompt` or `off`), `subagents.permission` (`allow`, `ask` or `passthrough`: the permission decision returned with a changed call, since auto mode can deny a call a hook changed without one) and `subagents.on_mismatch` (`warn` or `ignore`).
- `noonsight install` adds the two subagent hooks, and running it again upgrades an earlier install; `noonsight check` reports an install that lacks them or whose matcher was changed.
- Live tests for subagents (`NOONSIGHT_LIVE_LOGIN=1 npm run test:live`) run real sessions from the login of whoever runs them, with noonsight's hooks given through `--settings`, so nothing is installed into that account.
- `noonsight install` with no option now installs into the user settings of every Claude Code configuration directory of the account (`~/.claude`, the one in `CLAUDE_CONFIG_DIR`, and every directory in the home directory that holds a Claude Code configuration), with no administrator rights. It reaches logins whose organization delivers server-managed settings, where Claude Code ignores the managed settings files. `uninstall` removes them all. The machine-wide install moved to `noonsight install --managed`. See `docs/install.md`.
- `noonsight check` lists every Claude Code configuration directory and says which install reaches it, including a login whose server-managed settings shadow the machine-wide install, or turn its hooks off.
- `SessionStart` without a model, as in every `claude -p` run, now takes it from the `--model` argument of the Claude Code process, `ANTHROPIC_MODEL`, or the `model` setting, in Claude Code's order, and logs which one in `model_source` and `model_from`. It warns only when none names a model, or when the one that does cannot be pinned down. See `docs/hooks.md`.
- Session hooks: `SessionStart` and `PostModelSwitch` give each Claude Code session the rules for the model it runs on, and after `/model` say that the earlier rules no longer apply. They always exit 0, never use the network, and never block; an undeclared model only warns, and a refused configuration delivers nothing. See `docs/hooks.md`.
- Decision log: one JSON line per decision in `~/.local/state/noonsight/decisions.jsonl`.
- `noonsight install` and `noonsight uninstall`: for one Claude Code configuration directory with `--account <dir>`, or machine-wide with `--managed`, as noonsight's own file in Claude Code's `managed-settings.d/` (administrator rights once). Installing twice changes nothing, and other hooks and settings are kept. See `docs/install.md`.
- `noonsight check`: the configuration, every install, managed settings that stop hooks, the Claude Code version and the last decision.
- The rules for any model, scope and place must now fit in 9,500 characters, leaving room for the model-change note.
- Live tests (`npm run test:live`) drive real interactive Claude Code sessions; the tier that sends no prompt runs in CI against a pinned Claude Code version. See `docs/verification/claude-code.md`.
- TypeScript project with a test run on Node 20 and 22 in CI.
- Configuration schema (`schema/noonsight.schema.json`) and preset schema (`schema/preset.schema.json`).
- `noonsight resolve`: shows which rules a model receives for a task scope and a place, with the exact text that would be delivered.
- A configuration with any problem is refused whole, with its problems listed: schema problems first, then preset problems, then the rest.

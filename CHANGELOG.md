# Changelog

## 0.1.0

The first published version.

- `noonsight install` adds the hooks to every Claude Code login of your account, writes the configuration from the preset when there is none, and checks the result; `--account` covers one login, `--managed` the whole machine, and `noonsight uninstall` takes the hooks out (`docs/install.md`).
- Each Claude Code session and subagent receives the rules of the model it runs on, and receives them again when that model changes: at the start, after `/model`, compactions, `/clear`, resumes and forks (`docs/hooks.md`).
- The preset ships sourced rules for Claude Fable 5.2, Opus 5.5, Sonnet 5.5 and Haiku 5.5, on or off by default, and a new preset version is reported, or held until accepted (`presets/claude/SOURCES.md`, `docs/configuration.md`).
- Rules of your own, for one model or every model, limited by scope, place or trigger, for the machine or for one repository that each person trusts.
- `noonsight check`, `models`, `resolve` and `report` say what is installed, what each model receives and what was delivered.
- `noonsight run` starts sessions the hooks do not reach; routing, the classifier and the watcher for new logins are optional and off.
- The same package is a Claude Code plugin, with the repository as its marketplace.
- The package has no runtime dependencies and needs Node.js 20 or newer.
  It holds the compiled code without source maps, the preset, the schemas and the plugin's files; a publication builds from an empty `dist/` and runs `npm test` first, and a test holds the package to its list of files.

### Changes during development

- The README says what each result belongs to.
  One table of rule effects separates a rule delivered alone from the preset's rules together, each row with its result, runs per arm, cost, Claude Code version and evidence, and takes the place of the numbers scattered over the page; it names every rule with a measured effect alone, `fable-5-2/low-context-report` included.
  The guarantee is followed by its known limits; the benchmark's sessions are said to be real Claude Code sessions against a stand-in API; and the classifier is named as the one exception wherever the hooks' use of the network is (`docs/hooks.md` too).
  `docs/evidence.md` gains R16 to R19, computed from results already committed: the tests of each rule alone on Sonnet 5.5's bug, and the mean costs of the bug, the backlog and Fable 5.2's tasks; no existing entry's value changes.

- noonsight can be installed as a Claude Code plugin, as an alternative to `noonsight install` from npm, which stays the recommended install.
  The npm package is the plugin, the repository its marketplace, and each install covers one Claude Code login (`docs/install.md`, "As a Claude Code plugin").
  The plugin's first session start writes the configuration from the preset when there is none, its launcher (`scripts/noonsight`) finds Node.js where Claude Code has none on `PATH`, and its commands are skills, such as `/noonsight:check`.
  `hooks/hooks.json`, the manifests and the skills are generated from the code (`npm run plugin-files`), a test holds them and the version to it, and CI runs `claude plugin validate --strict`.

- Two installs that reach the same session deliver each event once: each copy of a hook claims the occurrence, and another kind of install that finds it claimed does nothing (`docs/hooks.md`, "One delivery per event").
  Before, a machine-wide install next to one in a configuration directory delivered the rules twice.

- `noonsight check` reports the plugin in each login and warns when an install reaches the same login; `noonsight install` and `noonsight watch enable` refuse to run from the copy a plugin holds; the decision log's `install` can be `plugin`, and `config_written` marks the start that wrote the configuration.

- A fork of a conversation now starts with what the conversation it copied holds.
  Claude Code forks three ways, `claude --continue --fork-session` or `--resume <id> --fork-session`, `/branch`, and `/fork`, each under a new session id with no record of its own, so a fork's start delivered its model's rules with no note retiring the other model's rules the copy held (F5), and a fork in a new process took the `model` setting instead of the model of the conversation's last response, which Claude Code runs it on (F6).
  The hook now finds the original, from the `forkedFrom` entries `/branch` writes, the background job of `/fork`, or the `--resume` id or the conversation `--continue` picks, and takes its record, last response and triggers; a fork whose original it cannot find gets a note that retires the rules of every model but its own (`from="*"`).
  The decision log records `fork_origin` and `forked_from` (`docs/hooks.md`, "Forks").

- In plan mode, Claude Code runs Sonnet for a session whose chosen model is Haiku, and reports that with a model switch, but the start of a compaction, or of a `/resume` typed in the session, still reports Haiku, so those starts and a `/clear` after them delivered Haiku's rules to Sonnet's requests (F7, F8).
  The session's record now keeps the chosen model while Claude Code runs another in its place, and a start in the same process that reports the chosen model keeps the one that runs; the log records `chosen_model` and `reported_model`.

- Claude Code leaves out a `SessionStart` context identical to one an earlier start added to the same conversation, so a resume or fork that delivered again rules a later note had retired, the startup's very text, reached no request (F9).
  A resume's or a fork's delivery now carries the time it was made in the opening tag of its note and its rules (`at="..."`), and never repeats an earlier one.

  Claude Code adds what the `PostModelSwitch` hook returns to the next request only, and drops it when another `/model` or the end of the session comes first; the hook recorded it as delivered all the same.
  So in a session started on Haiku, after `/model sonnet` and `/model fable` with no request between them, Fable read Haiku's rules from the session's start with no note saying they no longer applied, and a conversation resumed on the model a lost switch chose logged `already-delivered` and never got its rules.
  The session's record now keeps every model whose rules the conversation may hold without a note after them: each later note names all of them (`from` lists them, or reads `*` when their names do not fit), and a resume after a switch delivers the rules again.

- The installed preset's scopes are now declared for every configuration, since the package ships one.
- Task scopes: a scope can declare `match`, regular expressions run case-insensitively over a subagent's description and task text; the preset's scopes can declare them too, and a user scope of the same name replaces only the keys it gives. A session takes its scope from `NOONSIGHT_SCOPE`; a subagent from the scope whose matcher matches earliest in its task, and never from the session. An undeclared scope only means the rules for every scope. See `docs/configuration.md`.
- Place: `session.unattended_when_env` lists environment variables that put a session in the place `unattended`, so it receives the rules declared for sessions nobody is watching.
- The decision log records `scope`, `place`, `scope_source`, and when they apply `unknown_scope`, `scope_matcher`, `unattended_env` and `task_text_cut`.
- `noonsight check` reports two scopes whose matchers match the same example text, and says which scope and place sessions started from its environment get. A matcher that is not a valid regular expression, that matches every plain task text, or that has a shape known to backtrack catastrophically (a leading `.*` with no `^`, nested unbounded quantifiers such as `(a+)+`, or overlapping unbounded quantifiers in a row such as `\w+\w+`) refuses the configuration, naming the scope and the pattern.
- Live tests for scopes (`NOONSIGHT_LIVE_LOGIN=1 npm run test:live`): two sessions and two subagents on the same model, in two scopes, return different verification words.
- `noonsight watch enable` and `noonsight watch disable`: an optional watcher, off by default, that installs the hooks into each new Claude Code configuration directory made in the home directory, as `noonsight install --account <dir>` does. It runs as a launchd agent on macOS and a systemd user service on Linux, and watches only the entries directly in the home directory. `noonsight check` says whether it is on and runs. The first session of a brand-new login can still start without the rules; see `docs/install.md`.
- Subagent hooks: `PreToolUse` on the agent tool (matcher `Agent|Task`) predicts the model each subagent will run on, in Claude Code's order (fork, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, the call's `model`, the subagent's definition, the built-in subagents' own models, `CLAUDE_CODE_SUBAGENT_MODEL`, the parent's model), and adds that model's rules for the place `subagent` to the end of the subagent's task text. It never changes the model or the effort. `PostToolUse` compares the prediction with the model the subagent started on (`resolvedModel`), logs `match` or `MISMATCH`, and warns on a mismatch. An undeclared or unknown model only warns. See `docs/hooks.md`.
- Configuration: `subagents.delivery` (`prompt` or `off`), `subagents.permission` (`allow`, `ask` or `passthrough`: the permission decision returned with a changed call, since auto mode can deny a call a hook changed without one) and `subagents.on_mismatch` (`warn` or `ignore`).
- `noonsight install` adds the two subagent hooks, and running it again upgrades an earlier install; `noonsight check` reports an install that lacks them or whose matcher was changed.
- Live tests for subagents (`NOONSIGHT_LIVE_LOGIN=1 npm run test:live`) run real sessions from the login of whoever runs them, with noonsight's hooks given through `--settings`, so nothing is installed into that account.
- `noonsight install` with no option now installs into the user settings of every Claude Code configuration directory of the account (`~/.claude`, the one in `CLAUDE_CONFIG_DIR`, and every directory in the home directory that holds a Claude Code configuration), with no administrator rights. It reaches logins whose organization delivers server-managed settings, where Claude Code ignores the managed settings files. `uninstall` removes them all. The machine-wide install moved to `noonsight install --managed`. See `docs/install.md`.
- `noonsight check` lists every Claude Code configuration directory and says which install reaches it, including a login whose server-managed settings shadow the machine-wide install, or turn its hooks off.
- `SessionStart` without a model, as in every `claude -p` run, now takes it from the `--model` argument of the Claude Code process, `ANTHROPIC_MODEL`, or the `model` setting, in Claude Code's order, and logs which one in `model_source` and `model_from`. It warns only when none names a model, or when the one that does cannot be pinned down. See `docs/hooks.md`.
- Session hooks: `SessionStart` and `PostModelSwitch` give each Claude Code session the rules for the model it runs on, and after `/model` say that the earlier rules no longer apply. They always exit 0, never use the network, and never block; an undeclared model only warns, and a refused configuration delivers nothing. See `docs/hooks.md`.
- Decision log: one JSON line per decision in `~/.local/state/noonsight/decisions.jsonl`.
- `noonsight install` and `noonsight uninstall`: for one Claude Code configuration directory with `--account <dir>`, or machine-wide with `--managed`, as noonsight's own file in Claude Code's `managed-settings.d/` (administrator rights once). Installing twice changes nothing, and other hooks and settings are kept. See `docs/install.md`.
- `noonsight check`: the configuration, every install, managed settings that stop hooks, the Claude Code version and the last decision.
- The rules for any model, scope and place must now fit in 9,500 characters, leaving room for the model-change note.
- Live tests (`npm run test:live`) drive real interactive Claude Code sessions; the tier that sends no prompt runs in CI against a pinned Claude Code version. See `docs/verification/claude-code.md`.
- TypeScript project with a test run on Node 20 and 22 in CI.
- Configuration schema (`schema/noonsight.schema.json`) and preset schema (`schema/preset.schema.json`).
- `noonsight resolve`: shows which rules a model receives for a task scope and a place, with the exact text that would be delivered.
- A configuration with any problem is refused whole, with its problems listed: schema problems first, then preset problems, then the rest.

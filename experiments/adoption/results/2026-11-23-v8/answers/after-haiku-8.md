Verdict: adopt with conditions. Pilot it on a few machines first, on the Claude Code version the project measured.

Reasons:
- It addresses a gap the team likely has. The project measured that a user `CLAUDE.md` reached 46.9% of subagent requests (60 of 128), and `.claude/rules` reached the same share. Skills reached 0%. noonsight reached 100% (763 of 763) on the same kind of request (docs/evidence.md D20, D25, D26, D28, D27).
- Its delivery numbers are the strongest part of the evidence. Across 299 completed sessions on Claude Code 2.1.330, it covered 3,090 of 3,090 requests with rules due, and the 453 forks, `/resume`, plan-mode and file-editing-subagent requests were all covered (D18, D19, D21). Those sessions included `/model`, `/compact`, `/clear` and resumes, which is the switching your mixed-model setup does.
- It is cheap to run. It has no runtime dependencies, is MIT-licensed, and its hooks read only local files and never use the network. Each hook takes roughly 80 to 150 ms of CPU (D33).
- It makes per-model rules explicit and checkable. `noonsight report` shows what was delivered, and `noonsight resolve` prints the exact text a model gets for a scope.
- Its own evidence that the rules change behavior is narrow. The strongest result is `verify-changes`, which made Sonnet 5.5 and Haiku 5.5 run tests after a one-file fix in 29 of 30 and 27 of 30 runs, against 0 of 30 without it (R3, R14). That rule about doubles the cost of a small fix (R6: $0.0240 to $0.0505 per run).
- Its paid pilot found no measurable difference in pass rate on public tasks (B1: 133, 132 and 133 of 144 passed). Delivery is high, but that does not show a quality gain on general work.

Conditions and risks:
- Pin the Claude Code version. The delivery guarantee is measured on 2.1.330 only, and the project says hook behavior changes between versions. Test each Claude Code upgrade before the team moves to it, for example by running `noonsight check` and a few sessions per model.
- Decide the attended-session rules explicitly. Opus 5.5's and Fable 5.2's attended preset rules ship off. Fable's attended sessions get nothing from the preset until someone runs `enable`. Haiku's `carry-through` showed no effect in its test (R11). Choose what each model should get, rather than inheriting the defaults.
- Set `session.unattended_when_env` to your orchestrator's variable. Otherwise interactive sessions nobody watches are treated as attended. Headless runs (`claude -p`, the Agent SDK) are unattended by default.
- Know the limits on subagents. Workflow agents get no rules. Foreground calls of one type that need different rules give their subagents nothing until the first Edit, Write or agent call. Plugins the hooks do not read, including ones an organization syncs, leave their subagents on the parent's model. Explore and Plan subagents are covered.
- Known gaps: `/fork` is not available in a session started with `noonsight run` and rules. A conversation compacted with no response, then resumed with nothing that names a model, runs on Claude Code's default model, which noonsight cannot detect (1 of 300 sessions in the superseded run). Agent teams, routing and the classifier are not measured.
- Installation is per user, not per repository. `noonsight install` adds hooks to every Claude Code login on the machine. Organizations that set `allowManagedHooksOnly` or `disableAllHooks` block it. The package is not on npm yet (v0.1), so each person installs it from a clone with `npm install && npm run build && npm link`. Treat that as a supply-chain step, and pin the commit.
- The classifier is off by default. If turned on, it sends the first 4,000 characters of a task to a small model through the user's Claude Code login.
- Rule-based cost goes up. Rules that ship on add tokens to every request (`verify-changes` on Sonnet and Haiku). Watch the cost per run with `noonsight report` and the team's usage data.
- The main evidence is the project's own. The delivery numbers come from its own harness, which runs real Claude Code sessions against a local stand-in for the Messages API. It checks what the hooks return, not what the model did with it, and the project says delivery is not obedience. I read the documented numbers and their evidence map, but did not re-run `npm test`, which is what recomputes them from the raw files.

What it guarantees: in the current benchmark, every request under noonsight that had rules due received its model's rules, and no other model's rules were left unretired, across 299 completed sessions on Claude Code 2.1.330 (3,090 of 3,090 requests, 763 of 763 of them subagent requests). That rests on the project's own delivery harness, which uses real Claude Code sessions against a local stand-in API. It shows the hooks delivered the right text. It does not show that the models followed the rules, and it covers only the Claude Code version it was run on.

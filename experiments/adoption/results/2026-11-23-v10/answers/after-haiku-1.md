**Verdict:** Adopt with conditions. Pilot it on a few machines first, and treat it as a delivery mechanism for rules, not as a quality improvement.

**Reasons:**
- **It fits your mix of models.** Your team runs Opus, Sonnet, Haiku, and Fable, and many sessions start subagents. noonsight delivers each model its own rules, to the main session and to subagents, and re-delivers them after `/model` switches, `/clear`, compaction, resume, and fork (README.md:8-14, docs/hooks.md:59-68). A user `CLAUDE.md` cannot do this: it reached 46.9% of subagent requests in the author's run, against 100% under noonsight (README.md:41-44, docs/evidence.md D28).
- **The delivery numbers are specific, but they come from the author's own harness.** The current run reports 0 of 299 sessions breaking the invariant, and 3,090 of 3,090 due requests holding their rules, on Claude Code 2.1.330 (docs/evidence.md D18–D19). The sessions are real Claude Code sessions, but the Messages API is a local stand-in, so no model answered. The evidence page says `npm test` recomputes these numbers from committed raw files. I did not run the tests or check that.
- **There is no measured quality gain.** A paid pilot found 133 of 144 runs passing without rules, 132 of 144 under noonsight, and 133 of 144 with a `CLAUDE.md` (README.md:231, docs/evidence.md B1). The rule-effect results are on small tasks, and most preset rules have no measured effect (README.md:229).
- **Most of the preset is off for the places where your team mostly works.** Opus 5.5's and Fable 5.2's attended rules ship off, so an attended Opus or Fable session gets nothing from the preset until you turn rules on with `enable` (README.md:52, 184).
- **It is cheap to undo and does not block anything.** Hooks always exit 0 and never deny a call. `noonsight uninstall` removes it, and `NOONSIGHT_DISABLE=1` turns it off for one session (docs/hooks.md:15, 474-482).

**Conditions and risks:**
- **Pin and test Claude Code versions.** The results hold for 2.1.330 and earlier runs on 2.1.326–2.1.329. Several behaviors rely on details Claude Code does not document, such as `CLAUDE_CODE_SESSION_ATTENDED` (docs/hooks.md:123). A Claude Code update could change them silently. Before each update, run `noonsight check` and a few sessions, then read `noonsight report`.
- **Set `session.unattended_when_env` for CI and orchestrators.** Otherwise interactive sessions nobody watches count as attended and get the wrong rules (README.md:55, 259).
- **Know what the tool misses.** Workflow agents get no rules. Explore and Plan get rules through the agent-call hook, but a subagent started from a plugin noonsight does not read is predicted on its parent's model. A shared start with differing calls gives nothing. Edits made through `sed` or other shell commands do not reveal the `code-edit` trigger (docs/hooks.md:240-244, 391-401).
- **Decide whether your rules need to be per-model at all.** If every session runs one model with fixed rules, a `CLAUDE.md` is simpler (README.md:263).
- **Check that the hooks do what you expect.** Installing hooks into every Claude Code login on a machine is a real change to shared settings. The hooks run `ps` and `git ls-files` and can call `claude -p` when the classifier is on. The classifier is off by default, but if you enable it, it sends the first 4,000 characters of each task to a model through the person's login (README.md:254; docs/hooks.md:12). I read the docs, not the source or installer code, so review those before rolling out.
- **Verify on your own sessions.** Use `noonsight models` and `noonsight resolve <model> <scope> <place>` to see what each model will receive. Use `noonsight report` to see whether rules you care about are delivered, and drop any that never change anything you can see.

**What it guarantees:** Through Claude Code's hooks, noonsight puts the rules declared for a model into the requests of each session and subagent that runs on that model, and again after a model change, compaction, clear, resume, or fork. That is delivery, not obedience: a delivered rule is context the model may ignore. The guarantee rests on Claude Code's hook contract and on the author's benchmark run against Claude Code 2.1.330, with the API stubbed; it does not cover workflow agents, plugin subagents the tool does not read, or shell-based edits.

Verdict: **Adopt with conditions.** Run it as a time-boxed pilot on one pinned Claude Code version before rolling it out to the team.

Reasons:
- **The problem is real and measured.** The repo's own benchmark (D25 to D29) shows that a user `CLAUDE.md` reached 88.2% of requests with rules due and 46.9% of subagent requests, `.claude/rules` reached 76.3% and 46.9%, and one skill per model reached 0%. Your team runs many subagents, which is where the native options miss most.
- **The headline numbers match the raw file.** I spot-checked `experiments/delivery/results/claude-code-2.1.330/2026-11-23-c5b9130/summary.json`, and the covered and due counts behind D19 (3,090 of 3,090) and D20 (763 of 763) are there. I did not re-run the benchmark or the tests.
- **It covers the cases you use.** The docs claim coverage after `/fork`, `/resume`, plan mode and subagents that edit files, and in sessions started through `noonsight run`. Model is picked by model, scope, place and trigger, not by rule text, so your own rules get the same coverage.
- **It is cheap in what it does to the session.** The hooks never block, the classifier that sends text over the network is off by default, and the docs report about 80–150 ms of hook time per run.
- **Quality benefit is not shown.** In the paid pilot, 133 of 144 runs passed without rules, 132 of 144 with noonsight and 133 of 144 with a `CLAUDE.md` (B1). The rule-effect runs found no quality gain either (R8: 600 of 600 passed with or without rules). The only gains were behavioral: Sonnet ran tests after its edit in 30 of 30 runs against 0 of 30, and the bug-task result was 30 of 30 against 11 of 30 (R14, R15).
- **Cost goes up.** Mean cost per run on Sonnet's fix rose from $0.0240 to $0.0378 with the preset's three rules, and Haiku's roughly doubled, from $0.0015 to $0.0033 (R6, R7).

Conditions and risks:
- **Pin the Claude Code version and the noonsight version.** The results are per version: delivery was measured on 2.1.330, rule effects on 2.1.329 (Fable on 2.1.328), and CI pins 2.1.325 for live checks. Each hook fact in `docs/verification/claude-code.md` holds only for the version it was checked on. Confirm your team's version is in that list, or re-run `npm run test:live` on yours.
- **Run `noonsight report` on your own sessions.** It shows what was delivered, to which model, scope and place. It does not show whether a rule changed behavior, so judge the effect with your own tasks.
- **Set `session.unattended_when_env`** to your CI or orchestrator variable. Otherwise headless jobs are misread as attended sessions. Interactive sessions default to "attended."
- **Fable sessions get little from the preset.** The attended Opus and Fable rules ship off, so an attended Fable session gets nothing until you run `enable`. Decide whether you want those rules on.
- **Known gaps that matter for subagent-heavy use.** Workflow agents get nothing. Foreground calls of one type that need different rules give their subagents nothing until each one's first Edit, Write or agent call. A plugin noonsight does not read leaves its subagents on the parent's model. `/fork` is unavailable in sessions started by `noonsight run`. Agent teams, routing and the classifier are not measured.
- **Supply chain and trust.** It installs hooks into every login's `settings.json` and runs code on every session. Pin the npm version, and review the package and any `--managed` install before rollout. The repo is not a git checkout, so I could not verify that this directory matches the published package.
- **Repository rules are a risk.** A committed `.noonsight/noonsight.json` injects instructions into the model. Review its rule files in code review, and make sure each person runs `noonsight trust` deliberately.
- **Cost.** Budget for roughly a 50% to 100% rise in per-run cost on the small tasks measured, and check it on your own work.

What it guarantees: through Claude Code's hooks, each session and subagent receives the rules declared for the model it runs on, and receives them again after a model change, compaction, resume or fork. That rests on the repo's delivery benchmark, which ran real Claude Code 2.1.330 sessions against a stub API (no model answered), plus live checks on the versions it lists. It is delivery, not obedience, and it says nothing about your Claude Code version or whether a rule improves output.

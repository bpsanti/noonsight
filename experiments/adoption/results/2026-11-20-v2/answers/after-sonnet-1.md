**Verdict:** Adopt with conditions. Pilot it on a few people's machines first, not team-wide.

I read the README, `docs/hooks.md`, `docs/evidence.md`, `docs/usage.md`, the changelog and the delivery and benchmark READMEs. I did not run the tests or the tool, so the numbers below are the project's own, as committed.

**Reasons:**
- **It fits your setup.** It addresses mixed models and subagents directly. The hooks (`SessionStart`, `PostModelSwitch`, `PreToolUse`, `SubagentStart`) predict which model a subagent will run on and hand it that model's rules. A `CLAUDE.md` can't do that. Claude Code's documentation says built-in Explore and Plan subagents never load `CLAUDE.md`.
- **The delivery evidence is real.** The benchmark ran 300 random sessions of real interactive Claude Code 2.1.328. Sessions used `/model`, `/compact`, `/clear`, resume, subagents and edits, against a local stand-in for the API. 99.5% of requests with rules due held them (3,199 of 3,216), and 3 of 300 sessions broke the invariant (D1, D2). On the same first 60 sequences, a `CLAUDE.md` reached 87.3%, `.claude/rules` 70.9% and per-model skills 0%. Subagent coverage was 100% against 32.2% for the file-based options (D5–D11).
- **It is honest about its own failures.** The fuzzer found four real bugs (F1–F4), and the project documents them. Two were fixed before the 300-session run and two after. The 300-session fuzz has not been re-run on the fixed build, so the 99.5% figure predates F3 and F4. The numbers come from committed raw files, and `npm test` recomputes each one.
- **The hooks are low-risk to run.** They always exit 0, never block a call, don't use the network, and have a 10-second timeout. They cost 60–120 ms of CPU per run (D15). Each session can opt out with `NOONSIGHT_DISABLE=1`, and `noonsight uninstall` removes them. Every decision is logged and `noonsight report` summarizes it.
- **It sends less text than the alternative.** About 1,154 characters are added per request, against about 4,400 for a `CLAUDE.md` holding every model's rules (D13).

**Conditions and risks:**
- **Pilot first.** It is version 0.1, installed from a clone, not on npm. It also has a previous name, sextant. Pin the commit and the Claude Code version.
- **Pin and re-verify Claude Code.** Measurements cover versions 2.1.328 and 2.1.329. Delivery depends on hook behavior that Claude Code can change. Re-run `npm run delivery -- corpus` on each upgrade, and run `noonsight check` regularly.
- **Give sessions a scope.** The preset delivers little to a watched session with no scope. You need to set `NOONSIGHT_SCOPE`, `session.unattended_when_env`, and subagent `match` patterns. Without that, you would adopt it and see almost nothing delivered.
- **Delivery is not obedience.** A delivered rule is context only. Anything that must never be broken still needs a hook or a permission rule.
- **Rules change behavior and cost.** The measured effects are on small tasks with 30–40 runs per arm. `verify-changes` made Sonnet run the tests (30 of 30 against 0 of 30), but it doubled the cost of a cheap task ($0.0240 → $0.0505). Where the model already did the work, rules added cost and changed nothing. Haiku's `carry-through` showed no effect. In the larger SWE-bench pilot there was no measurable outcome difference, and the Sonnet and Haiku samples were small. Run `noonsight report` and drop rules that change nothing you can see.
- **Unmeasured paths you rely on.** The benchmark does not cover subagents that edit files, `/resume` inside a session, forks, plan mode, agent teams, the launcher, routing, the classifier or project configs. Subagents on plugin definitions, `--agents` definitions or agent teams get nothing or a guessed model.
- **Documented gaps that affect you.** Several parallel subagent calls of one type with different scopes can start with no rules. A compacted-then-resumed conversation with nothing naming a model runs on a default model noonsight can't tell. The 22 requests with another model's rules and no retiring note (D14) are the residual cost of the `/model` and resume design.
- **The test is partly self-referential.** The "right rules" reference is noonsight's own resolver, so a wrong resolution would not show up. The rule-effect and benchmark graders are Claude models. The repo also has an experiment that asks fresh Claude sessions whether to adopt the tool and scores the answers, and it contains a README rewritten for that experiment. Treat the framing with that in mind. The claims I checked against the committed docs held up.
- **Local state.** It writes state and a decision log under `~/.local/state/noonsight`, and the log can grow to 20 MB. Trusting a repo's `.noonsight/noonsight.json` lets that repo add rules to your sessions. By default a trusted project can only add rules, not change yours.
- **Skip it if it doesn't fit.** If most sessions run one model with fixed rules, a `CLAUDE.md` is simpler. The project says this itself.

**What it guarantees:** It guarantees that, in the tested lifecycle paths on one Claude Code version, each session and subagent request carries the rules resolved for its own model (99.5% of requests due, 3 of 300 sessions broken), and that rests on fuzzing real Claude Code sessions against a stand-in API, not on any measured effect on what the models then do.
